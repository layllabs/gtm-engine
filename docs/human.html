GTM Engine: signal-based outbound for local merchants

A pipeline that finds businesses where something just happened, dedupes them across sources, scores them against a configurable ICP with plain-English reasons, routes each one to email, a call or a walk-in, writes and lints the copy, classifies replies, and checks mailbox health before anything sends. One command, no dependencies, synthetic data in, a morning scoreboard out.

git clone https://github.com/layllabs/GTM-Engine && cd GTM-Engine
python -m gtm run
  • Scoring explains itself. Every account carries reasons in words, not just a number. See the scoreboard.
  • Routing is a table, not code. Who gets emailed vs called lives in one JSON file. A test guarantees nobody without an email is ever enrolled.
  • The CRM lifecycle is a state machine with an append-only event log. The diagram is parsed by a test and CI fails if it drifts from the code.
  • Copy has a lint gate. Em dashes, unfilled variables, spam phrases, more than one question: any of these blocks enrollment. Every line of every sequence is explained.
  • Deliverability has thresholds, not vibes. Bounce and complaint lines pull a mailbox out of rotation; two paused mailboxes retire the domain; a z-test stops me crowning an A/B winner on noise. Workflow 05.
  • Rules before the model. Regex handles bounces, OOO, unsubscribes and the obvious yes/no; Claude gets the ambiguous tail, against a JSON schema, with a non-model fallback. A 28-case labeled set scores the rules in CI. Prompts are versioned with the code.

What is not in the public repo: the discovery scrapers, the verifier, sequencer and CRM integrations. Those are API calls in the production version and belong to my employer. The schemas are the same, which is the point. Happy to walk through any of them live.

Writing

Cold email that owners actually answer. The full sequences, with a reason for every sentence and what the previous version got wrong, are in docs/copy. One example:

Most owners I talk to are paying a markup they never agreed to, buried in the statement. If you send me one recent statement, I'll show you line by line what you're paying and what it should be. No pitch until you've seen the math.
Why: owners don't feel "high rates", they feel "something on this statement doesn't add up". The ask is one photo, not a meeting. "No pitch until you've seen the math" removes the main reason not to reply.

How I work

Config over code

ICPs, routing, sequences and thresholds are JSON with schemas. Opening a new vertical is a new file. A rep can change who gets called without touching Python.

Every decision has a record

Short ADRs with the reasoning and the condition that would change my mind. Three so far.

Deterministic first, model second

Rules carry what rules can. The model gets what's left, against a schema, with a fallback. The rules double as the eval baseline.

Written down so it can be handed off

The sending-domain runbook takes a new domain from registration to first cold send. The SDR onboarding plan is how I bring a new rep to quota. Open questions is what I have not solved.

AI-assisted, human-owned

The code is written with AI. The scoring model, routing rules, copy and decisions are mine, and I review everything that touches a prospect.
